### Better Auth `additionalFields` (`src/auth.ts`)

```ts
user: {
  additionalFields: {
    firstName: { type: "string", required: false, input: true },
    lastName: { type: "string", required: false, input: true },
  },
},
```

This makes `firstName`/`lastName`:
- accepted as input on `auth.api.createUser` (via the `data` bag) and
  `auth.api.updateUser` (top-level fields on the update body),
- returned on the user object in session/`getSession`/admin `listUsers`
  responses,
- **not** required (nullable both at the DB and API level) — BE-2 can leave
  them unset on existing/legacy users.

No other change to `src/auth.ts`'s exports (`ac`, `viewer`, `manager`,
`admin_`, `auth` — same as DB-1's documented interface).

## Notes / gotchas

- Same Windows `@better-auth/cli` gotcha as DB-1: don't run
  `bunx @better-auth/cli generate` directly (fails building `better-sqlite3`
  without a native toolchain). Use the local devDependency already installed
  by DB-1 (`bun run node_modules/@better-auth/cli/dist/index.mjs generate
  --config ./src/auth.ts --output ./src/db/auth-schema.ts -y`).
- `bun run lint` reports 6 pre-existing `noStaticOnlyClass` biome warnings in
  `modules/*/service.ts` files — exit code 0 (warnings, not errors), not
  introduced by this task, not in `src/db/**`. Not fixed here since those
  files are outside DB-2 scope; flagging for the reviewer/BE-2 in case it's
  worth a follow-up.
- Scope note for BE-2: this task only swept `backend/src/db/**` for
  em-dashes/en-dashes per plan.md's explicit split ("sweep backend `src/db/**`
  comments too" for DB-2 vs. "sweep backend files (except `src/db/**`...)"
  for BE-2). I additionally fixed one em-dash I introduced in
  `src/auth.ts` (not `src/db/**`) as a courtesy, but did **not** sweep the
  rest of `src/auth.ts` or any other non-`db` backend file — that remains
  BE-2's item 7.
- `firstName`/`lastName` are plain nullable `text` — no format/length
  validation at the DB level (Better Auth's `additionalFields` type
  `"string"` doesn't enforce length either). If BE-2 or FE-2B want
  client/server-side length limits on the settings-page name inputs, that's
  their call, not a DB constraint.
- `name` is still the single source of truth Better Auth uses for display
  purposes elsewhere (e.g. it's what shows in existing UI that reads
  `user.name`); this task derives it as `firstName + " " + lastName` only in
  the **seed**. BE-2's plan item 6 ("Profile (D7): ensure Better Auth
  `updateUser` works for `firstName`/`lastName` (+ `name` derived as
  `firstName + " " + lastName` fallback username)") owns keeping `name` in
  sync when a user edits their profile via the settings page — this is a
  backend/API-layer decision (e.g. a `before` hook on `update-user`), not
  something enforceable at the DB level, so I did not add DB triggers or
  generated columns for it (would also hurt portability to Turso/D1-style
  SQLite).
